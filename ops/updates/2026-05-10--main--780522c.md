## Summary

Client-side photo compression in `StepPhoto` to keep Vercel from
rejecting DSLR-sized uploads.

After the d4518be fix surfaced real status codes, a real user upload
hit `Request failed (status 413). The photo is too large. Try one
under 4 MB.` on `/api/suggest-prompt`. Vercel caps serverless POST
bodies at ~4.5 MB and we were base64-encoding the original file
straight into the JSON payload — a 6-7 MB DSLR image becomes ~9 MB
after encoding, which the platform drops.

`fileToCompressedDataUrl` now sits between the file picker and the
Friend draft:

- `createImageBitmap` decodes the file, then a canvas downscales to a
  max long edge of 1600 px. That preserves enough detail for the
  OpenAI vision call AND the fal image-to-video upload (fal upscales
  internally anyway, so feeding it 4K+ buys nothing).
- Re-encoded as JPEG quality 0.85 with a tightening loop that drops
  quality 10 pts at a time if the data URL still exceeds ~3.6 MB.
- Falls back to the original FileReader path if `createImageBitmap` or
  the 2D canvas context aren't available (older browsers, exotic
  formats like HEIC on browsers that don't decode it natively).

Also clears `promptSuggestion` whenever the photo changes so the
"Suggest from your photo" button drafts a fresh sentence against the
new image instead of reusing a stale one.

## Blockers Or Risks

- HEIC files: Safari decodes natively via `createImageBitmap`, but
  Chrome/Firefox don't. The fallback path will base64 the original
  HEIC, which Vercel still rejects if it's over 4 MB. Workaround for
  affected users today is to convert to JPEG before upload. A future
  pass could ship a HEIC decoder shim if this becomes common.
- The 1600 px cap is a tradeoff: high enough that fal/Kling has detail
  to work with, low enough that JSON payloads stay well under 4 MB.
  If we change fal endpoints (e.g. switch to a model that demands
  higher resolution input), revisit this constant.
