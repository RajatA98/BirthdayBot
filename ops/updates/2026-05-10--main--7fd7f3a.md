## Summary

Two changes in one pass: fixed the Generate-button regression that was
leaving users stuck on the spinner even when the muxed mp4 was ready,
and shipped three zero-quality-risk latency wins that compound across
the planning and polling stages.

### Generation regression fix

`app/page.tsx`. The d9cde92 wizard rebuild introduced a cosmetic
progress-timer (`useEffect`, lines ~487-509) that incremented a fake
bar every 220 ms. Two bugs:

1. The timer was the ONLY thing flipping `setGenerating(false)` (it
   called it when the fake bar hit 100%). If the real fal job finished
   first, the UI sat on the spinner indefinitely. If the timer hit
   100% before the job finished, the UI flipped out of "generating"
   state while the job was still running — also bad.
2. `StepPreview`'s overlay branch was `(generating || isGenerating)`,
   which meant the rendering spinner shadowed the `<video>` element
   even after `generation.videoUrl` was populated.

Fix:

- The cosmetic timer now caps at 92 % and only drives the bar's
  visual width. It does NOT flip `setGenerating`.
- `generateVideo()` flips `setGenerating(true)` + `setProgress(0)` at
  the top, then `handleJob`'s terminal branch (`job.stage === "completed"
  || job.stage === "failed"`) flips both `setProgress(100)` and
  `setGenerating(false)`. Catch block also flips `setGenerating(false)`.
- The overlay branch is now `(generating || isGenerating) && !generation.videoUrl`,
  so a ready video always wins. Mirrors `components/creation-form.tsx`.

### Latency wins (safe-only)

1. **Photo compression tightened.** Constants in `app/page.tsx`:
   `MAX_PHOTO_LONG_EDGE` 1600 → 1280, `PHOTO_JPEG_QUALITY` 0.85 → 0.80,
   `SAFE_DATA_URL_BYTES` 3.6 MB → 3.0 MB. OpenAI vision uses
   `detail:"low"` (analyze-photo.ts:132) which internally downscales
   to ~512 px regardless, and fal upscales internally — so anything
   over 1280 px on the long edge is wasted bytes. Saves ~30 % on
   every /api/plan + /api/suggest-prompt body. Also gives more
   headroom against Vercel's 4.5 MB cap, reducing 413s.

2. **`analyzePhoto` in-process cache.** New Map<sha1Hash, Promise<PhotoAnalysis>>
   in `lib/tools/analyze-photo.ts`. When the user clicks "Suggest from
   your photo" and then advances to Brief, the SECOND analyzePhoto
   call (from plan-service) used to be a duplicate vision request.
   Now it resolves to the cached promise of the FIRST call (from
   suggest-prompt). Saves one full vision API call per session —
   roughly 2-3 s off the Brief load. Cache is process-local with a
   32-entry LRU; cold-start Lambdas re-analyze (correct) and warm
   ones reuse (fast). New `__resetPhotoAnalysisCacheForTests` export
   keeps the existing prompt-caching tests deterministic; new test
   proves two parallel calls collapse to one upstream request.

3. **Poll cadence.** `pollGenerationJob` interval 2200 ms → 3000 ms.
   fal-side status updates batch every 3-5 s anyway, so the extra
   800 ms is invisible to the user but cuts ~30 % of /api/jobs/check
   Lambda invocations. Attempts ceiling 160 → 120 keeps the total
   timeout ~6 min.

Combined: roughly 4-7 s shaved off the suggest → brief → generate
flow, plus fewer Lambda cold-starts.

## Blockers Or Risks

- The in-process analyzePhoto cache assumes the client sends the SAME
  data URL twice. After the photo recompression in 4dca0f2, that's
  the case (recompression is idempotent — same bytes in, same bytes
  out). If we ever add per-call mutation to the data URL, the cache
  will silently miss; not catastrophic, just defeats the optimization.
- Polling at 3 s means worst-case time-to-first-status is now 3 s
  instead of 2.2 s. Acceptable; status messages are aspirational
  during the queued/in-flight phase anyway.
- Model swaps (gpt-4.1-mini → gpt-4o-mini, eleven_v3 → turbo, kling
  lite) are deferred per user direction. They'd need A/B testing.
