## Summary

Real fix for the muxed-video-cuts-off-at-voice-end bug. The previous
patch (`9e20b12`) switched `amix duration=first → longest` but didn't
hold — `sidechaincompress` ends its output when its KEY input ends,
killing `music_ducked` at voice-end and dragging the amix output down
with it, which `-shortest` then propagates to the video stream.

Fix: `apad` the sidechain key (`voice_key`) so it lives forever
(silent after the real voice ends). `sidechaincompress` keeps running,
releases the music back to nominal volume after voice end, and the
audio stream stays alive for the full `-t` window. `voice_main` is
left finite so only the real voice mixes in.

Filter-graph change in `lib/tools/mux-voice-over.ts:148-167`:

- `asplit` now feeds `[voice_main][voice_key_pre]`.
- New step `[voice_key_pre]apad[voice_key]` makes the sidechain key
  infinite.
- `sidechaincompress` and `amix` are structurally unchanged.

## Blockers Or Risks

- The mux has no automated test coverage (ffmpeg runs in a temp dir
  with native binary; not easy to unit test). Verification path is
  local-real generation or a Vercel preview deploy. Worth eyeballing
  one fresh video before celebrating.

## Next Context

If the cutoff returns, the next things to suspect are:

1. `apad` defaulting to a non-infinite duration on older ffmpeg
   builds — pass `apad=whole_dur=…` explicitly if needed.
2. `-shortest` interacting with `-t` weirdly when a filtered output
   stream is non-monotonic. Dropping `-shortest` would also fix this
   case at the cost of frozen-last-frame tails when the fal video is
   shorter than the target.
3. The fal MP4 itself being shorter than expected — `durationForEndpoint`
   in `lib/tools/build-video-input.ts` controls that.

DRY follow-up: there's an identical `apad`/mix pattern in
`muxSongIntoVideo` further down the same file — it currently has no
sidechain so it's not affected by this bug, but if we ever add ducking
there too, apply the same key-pad trick.
