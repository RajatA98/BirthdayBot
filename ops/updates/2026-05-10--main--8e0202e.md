## Summary

Fix the live 413 on `/mothers-day` — "Couldn't build the brief.
Request failed (status 413). The photo is too large. Try one under 4
MB."

The Mother's Day page was sending raw photo data URLs straight to
`/api/plan`, hitting Vercel's 4 MB request body limit on any
modern camera photo. The BirthdayBot dashboard already solved this in
`344de73` / `8c089f5` via client-side downscale + JPEG re-encode
before stashing the data URL. This commit inlines the same pipeline
(`MAX_PHOTO_LONG_EDGE=1280`, JPEG quality 0.8 → 0.5 adaptive, 3 MB
cap) in `app/mothers-day/page.tsx`, so `onPhotoChange` runs
`fileToCompressedDataUrl` instead of `fileToDataUrl`.

## Blockers Or Risks

- Code is duplicated between `app/page.tsx` and `app/mothers-day/page.tsx`
  now. Worth extracting into `lib/client-photo.ts` next time we touch
  either page — both files have an identical 60-line block.
- iOS Safari < 17 doesn't support `createImageBitmap` from HEIC
  reliably; if it throws, we fall back to the original `fileToDataUrl`
  path and the 413 will reappear. Workaround: tell those users to
  shoot in JPEG, or transcode HEIC on the server.

## Next Context

If a 413 reappears, look at:
1. `MAX_PHOTO_LONG_EDGE` — drop to 1024 if needed.
2. `SAFE_DATA_URL_BYTES` — tighten from 3 MB to 2 MB.
3. `quality` floor — drop the `> 0.5` guard to 0.4 to let the loop
   compress further.

DRY refactor candidate: extract the trio
(`fileToCompressedDataUrl`, `ensureSafePhotoDataUrl`, `compressBitmap`)
