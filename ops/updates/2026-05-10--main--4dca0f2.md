## Summary

Just-in-time photo recompression so already-cached oversize photos
don't keep hitting Vercel's 413.

The 780522c compression only ran on the file-pick path
(`fileToCompressedDataUrl` inside `StepPhoto.onPhotoChange`). If a user
had picked a DSLR-sized photo BEFORE the 780522c deploy went live, the
raw uncompressed data URL was already persisted on the Friend draft
(via the dashboard's autosave to localStorage and via React state). On
the next call to `/api/plan` or `/api/suggest-prompt`, the body still
exceeded ~4 MB and Vercel returned 413.

`ensureSafePhotoDataUrl(dataUrl)` now sits in front of both calls in
`app/page.tsx`:

- If the data URL is under the safe threshold (~3.6 MB), no-op.
- Else, `fetch(dataUrl)` to get a Blob, `createImageBitmap` to decode,
  then route through `compressBitmap` — the same downscale-to-1600px +
  JPEG-0.85-with-tightening loop the file-pick path uses.
- On success, `update({ photoDataUrl: safePhoto })` writes the smaller
  data URL back to the Friend draft so the next call is cheap.

Wired into both `loadBrief` and `loadSuggestion`. The original
file-pick compression remains as the primary path.

## Blockers Or Risks

- The recompress step does add a few hundred ms before each call when
  it triggers. Acceptable: it only fires when the cached photo would
  have failed anyway, and only the first call within a session pays
  the cost (we write the result back).
- HEIC handling didn't change — Chrome/Firefox without native HEIC
  decode still fall through to the raw data URL and will fail at
  Vercel. Worth shipping a HEIC shim if this becomes common.
